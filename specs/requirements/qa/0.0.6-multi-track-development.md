# GRIPS Requirements Q&A Session 0.0.6

**Phase**: 0.0 (Prototype)
**Date Started**: 2026-08-09
**Participants**: Agent, Floppy Dog (Human)
**Purpose**: Define how GRIPS handles multi-track development, where several units of work progress concurrently in separate worktrees under separate agent sessions

---

## Source Input

The session input is a review comment from a downstream GRIPS project (pmus), not an agent-initiated question. The observation:

PROJECT-STATUS.md concentrates all active work into monolithic fields: one Current Stage, one Active Work sentence, and one narrative line per layer under Layer Synchronization. That shape assumes a single stream of work. When development runs as several concurrent tracks, in separate git worktrees, driven by separate agent sessions, every session must edit the same few lines. The result is merge conflicts on status prose and ambiguity about which track a given line describes.

The methodology needs first-class guidance for multi-track development: what a track is, how status is structured so concurrent tracks write to disjoint lines, and what a conflict in that file means.

---

## Question 1
**Asked by**: Agent

**Question**: What qualifies as a track? The draft defines a track by three properties held together: scope (exactly one unit of work), isolation (its own branch, and its own worktree when sessions run concurrently), and ownership (exactly one owning agent session, the single writer). Under that definition a phase's layer stage, a single feature, and an incident response are all tracks, while a direct one-line fix on the mainline is not.

Is the three-property definition the right test, and is a phase's layer stage genuinely peer to a feature track, or is it better modeled as the default track a project always has?

**My suggestion**: Keep the three-property test, because ownership is what makes single-writer status entries enforceable, and isolation is what makes line-disjoint merges necessary in the first place. Treat the layer stage as an ordinary track rather than a privileged one: a project with a single track uses the single-track shorthand in status and never notices the distinction.

## Question 2
**Asked by**: Agent

**Question**: Where does the track list live? Q&A 0.0.5 established pointer discipline: where a tracker exists, Outstanding Work references issues by number and never restates them. A per-track entry in PROJECT-STATUS.md (name, branch or worktree, current stage, next gate, links) sits close to that boundary, since a tracker could hold the same fields.

Should the Active Tracks list live in PROJECT-STATUS.md as drafted, or should status carry only pointers with the tracker holding track state?

**My suggestion**: Keep the list in PROJECT-STATUS.md. Pointer discipline exists to stop status from duplicating issue bodies; a track entry is not an issue body but the answer to "where are we now," which is exactly what status is for. The entry stays one line, and its links point at the issues and pull requests that hold the detail.

## Question 3
**Asked by**: Agent

**Question**: Should GRIPS prescribe branch and worktree naming for tracks (for example `track/{name}` and a sibling worktree directory), or specify only that the track name is stable and shared across branch, worktree, status entries, and pull request?

**My suggestion**: Specify the stable shared name and leave the prefix to project convention. Naming schemes are the kind of thing every project already has an opinion about, and the property GRIPS actually depends on is identity across artifacts, not the prefix.

## Question 4
**Asked by**: Agent

**Question**: Which version does this land in? The release increment rules (releases/README.md) assign new sections and significant additions to a minor increment (0.x.0) and clarifications to a patch increment (0.0.x). Multi-track guidance adds section 5.9, a glossary term, a mandatory rule, and amendments to 6.3. Main currently carries 0.0.2-dev, which has not been released.

Does this land as 0.0.3-dev (continuing the unreleased development line) or as 0.1.0-dev (matching the increment rules for new sections)?

**My suggestion**: The increment rules point at 0.1.0-dev, and the unreleased 0.0.2-dev content would fold into it. The draft carries 0.0.3-dev as instructed; the version string is a single-line change either way once this is answered.
